# Program-health SLOs (RC1-324)

SRE machinery pointed at a program: error budgets on the KPI agent's own
signals, generated by `python -m kpi.datadog slos --push` and upserted by
name like the dashboards and monitors. Everything here reads the surfaces
RC1-305 already ships — no new metrics were invented for this.

## The layering argument

Two layers, budgeted separately, because they answer different questions and
one must never hide inside the other:

**Layer 1 — can the numbers be trusted?** (the measurement system)

| SLO | SLI | target |
| --- | --- | --- |
| Program measurement health | % of time the *unmeasured* monitor sat in OK — no KPI stale or broken | 99 % / 30d |
| Program pipeline liveness | % of time the *heartbeat* monitor sat in OK — readings actually landing | 99 % / 30d |

**Layer 2 — is the program healthy?**

| SLO | SLI | target |
| --- | --- | --- |
| Program health | % of time the *tripped* monitor sat in OK — no KPI over its so-what threshold | 95 % / 30d |

The targets encode a deliberate asymmetry (a test enforces it): a program is
*allowed* to run red 5 % of the window — red sometimes is what thresholds
are for, and the budget is what separates normal red from escalation-worthy
red — but the instruments only get 1 % of rot. If the two budgets met, a
dead collector could quietly spend the budget meant for real program
trouble, which is the same honesty rule the readings carry (`ok` / `stale` /
`broken` never conflated with a value) restated in SLO form.

**Fleet objective** (one, account-wide): *Agent fleet reliability* — the
share of the fleet's model calls that completed without error, 97 % / 30d,
from the APM trace metrics the RC1-322 LLM Observability spans generate.
`default_zero` on the error series, because `trace.anthropic.request.errors`
only materialises after the first error — a fleet that has never failed must
read 100 %, not no-data.

## Provisional targets, on purpose

99 / 99 / 95 / 97 are starting points, not conclusions: a target should come
from an observed baseline, not a wish. After two weeks of soak, calibrate
against the actual burn — the simulated program's planted events (the day-29
slip, the week-6 cost spike, the day-43 source break) are *scripted* to burn
these budgets, so the sim doubles as a live demonstration that the burn-down
math works. Note when calibrating: the sim's burn is intentional; only the
eval store's burn is evidence about targets.

## Order of operations

Monitor-based SLOs need their monitors to exist, and the dashboards gain an
error-budget row only once the SLOs exist:

```bash
python -m kpi.datadog monitors --push
python -m kpi.datadog slos --push
python -m kpi.datadog dashboards --push
```

`slos --push` refuses with a pointer to `monitors --push` if a monitor is
missing. SLOs live in the UI under **Service Mgmt → SLOs**, filterable by
`generated:kpi-datadog`.
